# 设计边界

[English](boundaries.md)

> dsh-rewind 只做一件事：把对话就地回退到更早的用户消息，可选地一并还原那一轮改过的文件。本文约定这件事的职责范围：每条边界都写明决定、它为什么停在这里、以及这个需求由谁满足。列在这里的行为都是有意为之或已经接受的；缺陷是另一回事——行为与本文或其它已写明的契约相矛盾，缺陷会被修复，不会收进这份清单。

## 定位

对话回退是产品。文件还原是附加：回退通常意味着“把那一轮对文件的改动也退回去”，写前检查点足够支撑这件事。本插件不是工作区历史系统、不是会话管理器、也不是供其它插件搭建的底座，并且不会长成其中任何一个。它是 Agent 工作流里的一个插件，不是工作流本身。

两条规则让它保持小：

- 一个插件只做一件事，适配跟随上游的 DSH 线；
- 没有第二个使用者之前，不做抽象。

## 一览

| 边界 | 分类 | 为什么停在这里 | 需求归属 |
| --- | --- | --- | --- |
| 文件还原覆盖 Agent 的 `write`/`edit` 文本编辑与已跟踪文件，不是整棵树 | 按设计 | 写前检查点模型自带这条边界；整树历史是另一类产品 | Git，或项目已经在用的快照工具 |
| 回退是单向的；会话日志只追加 | 按设计 | 只追加是审计与崩溃安全的地基；这次裁剪是一次替换操作 | DSH「在新对话中分支」 |
| 适配跟随上游 | 按设计 | DSH 处于开发者预览；只适配新线，行为才稳定、门禁才有意义 | 为你的 DSH 线构建的那个版本 |
| 隐藏与回退按钮接入官方路径（私有接缝） | 上游约束 | 宿主没有公开席位；只有宿主自己的路径能保证行为与时机一致 | 上游席位；在此之前每条 DSH 线重新核对 |
| 子代理会话不追踪 | 按设计 | 子代理有自己的会话，父会话对它的文件没有权限 | 子代理会话自身，或 Git |
| 不做整树快照，不碰 git | 按设计 | 工作区历史已有归属；refs 与索引属于项目自己的工作流 | Git |

## 文件边界

本插件面向的工作流，是 Agent 通过 `write` 与 `edit` 编辑文本。对这条工作流，记录在机制上是确定的：写前就取到了改动前的状态。插件也会在每条用户消息边界复查已跟踪文件，让已跟踪文件的外部改动在下一条消息边界进入记录——这是低成本的兜底，不是保证。还原只写回备份，并与真实磁盘对账。机制与具体情形见[文件回退的追踪边界](compat/tracking-boundary.zh.md)。

边界来自模型本身：从未被写类工具处理过的文件不会进入追踪列表；没有被备份的那段状态，无法写回。它宁可不动，也不猜测：

- 首次写类处理之前的历史，没有备份；
- 未被备份的那段状态（超过单文件上限、快照备份被关闭），无法跨越还原；
- 追踪列表之外的文件不会被追踪；自定义组合挂载的、默认 `write`/`edit` 之外的写工具，其编辑也不在还原范围内。

这就是 Claude Code 使用的写前检查点模型；边界由模型自带，不是这一版实现的捷径。工作区历史已经有更好的归属：Git 逐字节地记录它，而且 Agent 本来就在用这套工具与习惯。在对话插件里再造一份，等于复制一个已经有人维护的权威；两份权威迟早会对不上。

真在这里做全树存储，代价是实打实的：

- **范围**——第二份存储需要索引、排除、清理、大仓库行为和二进制处理；插件会变成一个带“回退按钮”的快照引擎；
- **存储**——项目通常已经有承载历史的仓库；再按消息存一份工作区内容，是重复占用，还要自带一套 GC；
- **风险**——每条消息捕获整棵树会带来 IO、延迟和一整类失败模式（权限、链接、忽略目录、超大文件），每一种失败模式都是需要扩张安全边界才能覆盖的变更面；
- **维护**——快照引擎的成本是持续性的，Git 的成本由整个生态摊薄。

这些都不是“插件做不到”的理由，而是“这件事不该在这里做”的理由。需要任意文件在任意更早时刻的状态，用 Git；本插件不承担这个职责。把它当作便利，而不是工作区的安全网。

## 单向的回退

一次回退只追加一条标记（一条带 surface `replace` 的 `user/message`），日志从不重写。原始历史仍在：搜索、遥测、轨迹面板与 `/export` 仍能看到被撤回的内容，也没有原地撤销。这两件事是同一性质的两面——对只追加的记录做一次模型上下文层面的裁剪，而不是删除。

这是有意的：

- **可审计**——发生过什么，记录就是日志，回退不改写它；
- **崩溃安全**——一次追加是可能的最小变更，要么落盘，要么没有落盘；
- **可预测的界面语义**——“反向回退”会是插件自创的第二套 surface 语义，还要与压缩、分支、分页逐一交互。插件只切一刀，然后停手。

如果被撤回的内容还要继续，用 DSH 的分支：在你想保留的那条消息上「在新对话中分支」。删除或脱敏已记录的内容，是宿主的数据操作，不是回退功能。

## 适配跟随上游

DSH 处于开发者预览阶段，迭代很快，行为在相邻线之间会变。上游变化、插件需要适配时，新版插件只适配并维护新的 DSH 线；不做多通道设计，也不做跨版本兼容。这是功能稳定性和可维护性的选择，对一个迭代这么快的宿主来说也是规范做法。

预发布遵循同样的节奏：DSH 迭代时通常会先发 alpha 内测版，插件同样以 alpha 内测版跟随适配，行为与上游保持一致；`latest` 依然面向最广泛的用户，留在被广泛使用的那条线上。

由此得到这条边界：一次只适配一条线。

- 旧线保留为它构建的最后一版，放在对应 release 分支上——仍在分支上维护，只是不再随主线向前走；
- `engines.dsh` 声明适配的那条线；范围外的运行时在装载阶段就不被接纳——未适配的代码不会跑起来。这次拒绝是安全属性，不是障碍。

在一个代码库里同时扛多条线，意味着多个验证目标、多套兼容补偿和大量未经验证的交叉组合，装载门禁也会随之失去意义。把插件版本对上 `dsh --version`，是更小、也更诚实的取舍。代价说明白：想用最新功能就升级 DSH；否则留在旧版本线的最后一版。机制见[发布与 DSH 版本对齐](release/release.md)。

## 私有接缝走官方路径

隐藏被撤回的内容和提供回退按钮是同一类问题：宿主对两者都没有公开席位。插件不从外部复刻它们，而是接进宿主自己走的那条路——撤回区间交给 Chat 构建器的 `visibility` 输入，按钮直接放进行自己的操作行。代价只有维护：DSH 换线时重新核对这两条接缝，清单见[兼容性审计](compat/audit.md)。

收益是插件的行为与官方界面一致，而不是并排另立一套：

- **隐藏走官方路径**——被撤回的行离开排序、分组与回合导航的方式，与官方隐藏行完全相同，因为它就是其中之一。
- **按钮与行自己的控件同源**——与 Copy 在同一次提交里成为兄弟节点，出现、隐藏、卸载都与它同步，不需要自己的时序。
- **界面其余部分不付代价**——按钮是渲染的一部分，不是对渲染的观察：没有 DOM 全量扫描，也没有每次变更重新查询，界面其他功能不会因此变慢或变样。（未读插话气泡是例外，但仅在它存在时才扫描，由 inbox 门控。）

没有可直接接进去的官方路径时——例如进程内的分页读取——插件就不做：宁可让用户手动「加载更早」，也不为隐藏行再补一层分页。

## 子代理，以及“极简”的含义

子代理运行在自己的会话里。它的文件不会被备份，父会话的回退也无法还原；插件不为子会话保留快照，也不在子会话内提供回退。这与插件在其它地方的范围规则一致。

“极简”不是审美。它意味着没有插件框架、没有为假想宿主准备的适配层、没有跨版本线的兼容垫片：每一层抽象都是需要维护、验证和加固的面。插件小，失败模式才数得清。

## 缺陷还是边界

- **按设计**——在契约之内；边界是有意的，需求有归属。
- **上游约束**——宿主没有提供该输入；插件接入最近的官方路径，或干脆不做，并记录在兼容性审计里。
- **缺陷**——行为与本文、其它已写明的契约或测试相矛盾。缺陷会被修复；修好的缺陷不会当作边界保留。

本文与代码不一致时，那是本文的缺陷：以实现和已写明的契约为准，顺序如此，然后订正本文。希望某条边界被跨过，是一个产品诉求；它按上面的理由权衡，本身并不构成缺陷。

## 边界什么时候会移动

边界在产品目标改变时移动——例如文件历史成为产品本身，或 DSH 补上了缺失的输入——而不是因为某个用例希望它移动。在那之前，分工不变：本插件负责对话，以及一次回退所需的那一小片文件状态；工作区的历史由 Git 负责。
