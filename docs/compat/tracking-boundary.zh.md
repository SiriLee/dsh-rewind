# 文件回退的追踪边界

> 本文说明文件回退的**追踪范围**与**精度边界**：哪些文件与改动会被记录、还原时能得到哪个时刻的状态，以及这些边界为何不再扩展。
>
> 要点：**被写类工具（`write`、`edit`）改动过的文件始终可以精确还原**——插件在改动落盘之前捕获了原内容；**命令行或手动编辑**只有在该文件已被写类工具处理过之后才进入追踪，且其记录滞后一条消息，因此这类改动不总能精确对齐到指定消息。这些边界均为**有意取舍**（与 Claude Code 的检查点语义一致），不是缺陷。

## 追踪范围：插件如何得知文件发生了变化

文件在 DSH 中只有两种变化途径，插件对二者的可观测性完全不同。

**写类工具调用（`write`、`edit`）**：调用参数给出了确切的文件路径，插件可在写入落盘**之前**把该文件的当前内容原样复制到备份目录。这条路径是确定性的——一经处理即可还原，文本、二进制、非 UTF-8、CRLF 均逐字节一致，原始权限位一并记录。

**命令行或手动编辑**（bash 中的 `sed -i`、PowerShell 写入、构建脚本、编辑器保存）：没有任何环节向插件声明被修改的路径，因此**不存在可以在改动前捕获的对象**。插件只能事后发现它，依据两项机制：**追踪列表**（文件被写类工具处理一次即加入），以及**消息边界复查**（每条新的用户消息到达时，核对追踪列表中每个文件当前的磁盘内容与最近一次记录是否一致，不一致则记录当前内容）。

## 记录语义：一条记录表示一条消息开始时的状态

插件不保存工作区的当前状态，保存的是**状态转变**。每条记录回答同一个问题：

> **这条消息开始时，这个文件是什么？**

记录锚定在触发它的那条用户消息上，内容有两种形态：`null` 表示该时刻文件**不存在**（还原时表现为删除），否则为一份字节副本。两种来源都符合这一语义：

- **写前捕获**：在 `edit` 落盘**之前**取内容，即该消息开始时（改动发生前）的状态；
- **边界复查**：在新消息到达时取当前内容，即该消息开始时的状态。

同一条消息的回合内多次改动同一文件会产生多条记录；还原时取其中**最早**的一条，即该消息开始时的状态。

## 还原语义：从目标消息向后取最早的记录

回退到消息 *M* 时，对每个文件在 **M 及其之后**的记录中取**最早**的一条（其锚定消息最靠前，同一消息内记录时间也最早），把该记录的内容写回磁盘；写入前先与磁盘比对，一致则不做任何操作。因此只有真正不一致的文件会被改动，重复回退也不会反复覆盖。

为什么不取"*M* 之前最近"的一条？因为它可能早于一段**没有任何记录**的区间（典型情形是文件超过体积上限、插件拒绝备份的那一段），写回它等于用更旧的版本覆盖当前文件。插件在此处的取舍是：**宁可少还原，也不写错内容。**

以"新建 → 只聊天 → 只聊天 → 编辑 → 命令改写"为例：

| 消息 | 回合内发生 | 文件内容 | 记录（该消息开始时的状态） |
| :---: | --- | :---: | --- |
| 1 | `write` 创建 | `—` → `A` | `null`（落盘前该文件不存在） |
| 2 | — | `A` | `A`（磁盘内容与上一条 `null` 不一致） |
| 3 | — | `A` | （无：与上一条一致，不重复记录） |
| 4 | `edit` `A` → `B` | `B` | `A`（本次编辑之前的内容） |
| 5 | `bash` `B` → `C` | `C` | `B`（命令执行之前的内容） |

磁盘当前为 `C`。回退至消息 5 得到 `B`，消息 4 得到 `A`；消息 3 自身没有记录，向后取最早的一条，即消息 4 的记录 `A`——正是消息 3 开始时的状态；消息 1 的记录为 `null`，于是删除该文件。

## 边界

### 文件从未被写类工具处理

进入追踪的前提是被写类工具（`write`、`edit`）处理过一次。在此之前，该文件经历的所有命令行或手动改动都没有记录，回退到任何消息，插件都只能报告"没有可还原的改动"。

与之同源的情形是：文件在模型首次处理它时**已经存在**，那次记录的是**当时**的内容。因此回退可以到达该时刻，但无法回到更早——更早的历史插件未曾观测。

### 外部改动的记录滞后一条消息

写类工具在改动前主动交出路径，命令行改动没有这一环节：它要等到**改动之后的下一条用户消息**到达，才被消息边界复查发现，而复查记录的是**发现时**的内容，即改动**之后**的状态。因此"改动前的状态"并不记录在发生改动的那条消息名下，而是记录在**更早的那条有记录的消息**名下。

由此，当目标消息 *M* 名下**没有**该文件的记录时（*M* 开始时的状态与上一条记录一致，因而没有产生新记录），插件取到的是"*M* 及其之后最早被记录的那条消息**开始时**的状态"。若这段区间内的改动都由写类工具完成，该状态就等于 *M* 开始时的状态；若其中有一次命令行改动，那条记录记的就是改动**之后**的状态，回退结果便落在更靠后的那个状态上。例如：

> 消息 2 记录了 `A`；消息 3、4 名下都没有记录；消息 5 的回合里命令把文件改成 `B`，消息 6 的边界复查记录了 `B`。此时回退到消息 3、4、5 得到的都是 `B`（改动之后的状态），而它们开始时的状态其实是 `A`；回退到消息 2 即可取回 `A`。

具体表现取决于此后的变化：磁盘与那条记录一致时，插件不做任何操作；此后文件又变过时，写入的是那个中间状态；若那次改动是删除文件、而 *M* 开始时文件仍然存在，则表现为**删除当前文件**——机制与前述情形相同，只是记录的内容为 `null`。需要改动前的内容时，回退到记录着该内容的那条更早的消息即可：内容始终保存在备份中，"回退到 *M*"只是不一定会落在它上面。

### 单文件体积上限

写入前若文件已超过体积上限（默认 8 MiB，可用 `DSH_REWIND_MAX_FILE_BYTES` 调整，设为 `0` 关闭），插件不记录、也不复制其内容：其状态变化要等文件回到上限以下之后，才由下一次消息边界复查重新记录；从未被写类工具处理过的文件也不会因为体积过大而进入追踪。还原另有一道门禁：磁盘上当前超过上限的文件一律不动——绝不用一份更旧的记录覆盖它。

## 设计取舍

要覆盖"从未被写类工具处理"的文件，插件必须知道任意命令修改了哪些文件，只能对整个工作区做全量追踪、反复生成整树快照——体量极大，且正是 Git 等专业快照工具的职责。

要让每条消息都精确对应自身时刻的状态，要么在每个消息边界记录**全部**被追踪文件（无论是否变化），要么让所有命令行改动都具备改动前通知；而"未改动任何文件的消息"占绝大多数，代价是存储量随对话长度线性增长。

插件接受上述边界，换取轻量、可预测，以及**绝不写错内容**。需要工作区级别的精确历史时，请使用 Git。
